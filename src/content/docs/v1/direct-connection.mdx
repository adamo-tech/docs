By default, video travels **browser → Adamo router → robot**. A direct connection (peer-to-peer) sends it **straight between the browser and the robot** over WebTransport, cutting out the router hop for lower latency.

It's **additive and automatic**: the browser uses the direct path when one is available and silently falls back to the relay when it isn't — so nothing breaks, you just get lower latency where the network allows it.

## When it's used

A direct connection is used only when **all** of these hold — otherwise the session stays on the relay, which always works:

- **The robot opts in** to serving P2P (see below). Robots don't serve it by default.
- **A direct network path exists** between your browser and the robot: the same LAN, the same [Tailscale](https://tailscale.com) tailnet, or a robot with a publicly reachable IP. Robots behind symmetric CGNAT (for example Starlink) usually can't be reached directly and stay on the relay.
- **You're on Chrome / a Chromium browser.** The direct path pins a self-signed certificate, which only Chromium supports; Safari and Firefox fall back to the relay.

## Enable it on the robot

The robot has to opt in. Add one call to the robot you already have (see [Quickstart](/v1/quickstart/)):

The Python SDK 1.0 has no `p2p=` option. Its video tracks take `route=` instead: `"auto"` (the default) races a LAN candidate against the relay, `"relay"` never dials one, and `"local"` requires the direct link named by `direct_target`.

```python
import adamo

robot = adamo.Robot(api_key="ak_...", name="my-arm")
robot.attach_video("main", device="/dev/video0", route="auto")
robot.run()
```

The P2P listener is additive — the robot keeps its normal relay connection, so operators who can't reach it directly still see video over the relay.

## Use it in the browser

Nothing to configure. Open the robot on [operate.adamohq.com](https://operate.adamohq.com) in Chrome and it connects directly when it can.

- Chrome may show a one-time **"allow local network access"** prompt the first time — click **Allow** (it persists for the site).
- To confirm you're direct, open the [Control Panel](/v1/web-interface/#control-panel) latency breakdown: the path shows **`you ↔ robot (direct)`** instead of the router hops.

## Best results: Tailscale

The most reliable way to get direct connections across different networks is to put **both the robot and the machine running your browser on the same [Tailscale](https://tailscale.com) tailnet**. The robot then advertises its tailnet address as a candidate, and the connection works **regardless of NAT** — including symmetric CGNAT / Starlink, where a raw direct connection can't be established. The robot must be reachable on its P2P port over the tailnet's ACLs.

## Force the relay

Direct connections fall back to the relay automatically, but you can also force relay-only for a browser session — run this in the browser console and reload:

```js
localStorage.setItem('adamo_p2p', '0')
```

## Fully local: no API key or relay

A robot can also stream with **no Adamo account, API key, or internet connection**. Use this on an isolated network, on a bench, or between two processes on the same machine. The robot serves video itself, and a receiver connects to it with the robot's address and a **pairing key**. Nothing goes through the Adamo network.

Requires SDK **1.0.17** or later on both the robot and the receiver.

### Stream from the robot

Run your usual robot script **without an API key**. When neither `api_key` nor `ADAMO_API_KEY` is set, `adamo.Robot()` warns and starts as a local robot instead of connecting to the relay. The same script therefore streams through the relay when the key is set and locally when it isn't:

```python
import adamo
import numpy as np

robot = adamo.Robot(name="my-arm")  # local when ADAMO_API_KEY is not set

track = robot.video("front", pixel_format="BGR", width=640, height=360, fps=30)
frame = np.zeros((360, 640, 3), dtype=np.uint8)
for _ in adamo.Rate(30):
    track.send(frame)  # or a frame from your camera
```

The local robot listens on port **17447**: UDP for video and TCP for pairing. At startup it prints the pairing key to hand to the receiver:

```
adamo: warning: no API key was found (pass api_key or set ADAMO_API_KEY), so my-arm is running locally without the cloud. It will not appear on operate.adamohq.com, and recording and inference are unavailable.
adamo: connect on this network with address <this machine's IP>:17447 and pairing key <pairing key>
adamo: from Python: adamo.connect_local("<ip>:17447", "<pairing key>")
```

An API key that is set but invalid is still an error; the robot only runs locally when no key is present at all.

To always run locally, whether or not a key is set, use `adamo.Robot.local()`. It also takes a different `port` and a fixed `pairing_key`, and reports them as `robot.local_port` and `robot.local_pairing_key`.

Hardware-attached tracks (`robot.attach_video(...)` then `robot.run()`) work the same way as on a cloud robot.

The pairing key is generated when the robot starts, so a new key is printed on each run. To keep the same key across restarts, pass the first run's key back in with `Robot.local()`:

```python
robot = adamo.Robot.local("my-arm", pairing_key="<key printed on the first run>")
```

Treat the pairing key like a password: anyone on the network who has it can watch the robot's video and send it control messages.

### Receive in another process

Connect with the robot's address and pairing key, then open a video receiver exactly as you would over the relay:

<Tabs syncKey="lang">
<TabItem label="Python" icon="seti:python">

```python
import adamo
import numpy as np

with adamo.connect_local("192.168.1.20:17447", "<pairing key>") as session:
    with session.video_receiver("my-arm", "front", max_queued_frames=1) as receiver:
        while True:
            frame = receiver.recv(timeout=5.0)
            rgba = np.asarray(frame.rgba)  # uint8 (height, width, 4)
```

</TabItem>
<TabItem label="Rust" icon="seti:rust">

```rust
use std::{sync::Arc, time::Duration};
use adamo::{Session, video_receiver::VideoReceiver};

fn main() -> adamo::Result<()> {
    let session = Arc::new(Session::connect_local("192.168.1.20:17447", "<pairing key>")?);
    let receiver = VideoReceiver::subscribe(session, "my-arm", "front", 1)?;
    loop {
        // None means no frame arrived within the timeout.
        if let Some(frame) = receiver.recv(Duration::from_secs(5))? {
            println!("{}x{} seq {}", frame.width, frame.height, frame.sequence);
        }
    }
}
```

</TabItem>

On the same machine, use `127.0.0.1:17447`. The address can omit the port when the robot uses the default `17447`.

### Things to know

- **Only one local robot per port.** A second `Robot.local()` on the same machine fails with *Address already in use*. Give it another port with `adamo.Robot.local("other-arm", port=17448)`.
- **The robot's firewall must allow UDP and TCP on its port** for receivers on other machines, for example `sudo ufw allow 17447` with `ufw`.
- **Local robots are invisible to the cloud.** They don't appear on operate.adamohq.com and can't be recorded by the Adamo data service.
- **Linux and macOS only** for the receiver.

## Notes

- Direct connections are **authenticated and org-scoped**, and teleop minutes are **metered**, exactly like the relay.
- If a direct connection drops mid-session, video continues over the relay.
- P2P carries **video** (and teleop) directly; discovery, fleet presence, and the robot list still go through the Adamo network as usual.
