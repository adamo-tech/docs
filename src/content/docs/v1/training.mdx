The Python SDK trains policies on Adamo's GPUs with the API of [Tinker](https://tinker-docs.thinkingmachines.ai): your training loop runs on your machine and sends batches, and the model and its optimizer stay on the server's GPU. Requires SDK 1.0.10 or later.

```python
import adamo
from adamo import types

service_client = adamo.ServiceClient()   # authenticates with ADAMO_API_KEY
training_client = service_client.create_lora_training_client(base_model="nvidia/GR00T-N1.7", rank=32)

for step in range(2000):
    data = next_batch()   # a list of types.Datum
    forward_backward_future = training_client.forward_backward(data, "flow_matching")
    optim_step_future = training_client.optim_step(types.AdamParams(learning_rate=5e-4, grad_clip_norm=1.0))
    forward_backward_future.result()
    optim_step_future.result()

weights = training_client.save_weights_for_sampler(name="stack-v1").result()
training_client.save_state(name="stack-v1").result()   # what robot.inference(lora="stack-v1") runs
```

To run what you trained on a robot, pass the same name to `robot.inference`: see [Running a trained policy](#running-a-trained-policy).

## How calls run

`forward_backward` adds the gradients of a batch, and `optim_step` applies AdamW to the gradients added since the last step, then clears them. Both return an `APIFuture` as soon as the server has queued the call. The server runs calls in the order they were made, so queue the next step before waiting on the current one and the GPU always has work.

- `future.result(timeout=None)` waits for the result. A `timeout` raises `TimeoutError` and leaves the call running; call `result()` again to keep waiting.
- `await future.result_async()` and the `*_async` methods (`forward_backward_async`, `optim_step_async`, ...) serve async code. Each `*_async` method returns the `APIFuture` once the call is queued.
- Several `forward_backward` calls before one `optim_step` add up their gradients, for a larger effective batch.
- A call the server rejects as invalid raises `ValueError` with the server's reason, such as an unknown camera name. Network and server errors are retried for up to 5 minutes, and each retry prints its cause.

`adamo.ServiceClient(base_url=None, api_key=None)` connects to Adamo's training server; `base_url` or the `ADAMO_TRAINING_URL` environment variable points it at another one. The server starts a GPU on the first call, so `create_lora_training_client` can take about a minute.

## Data

Tinker trains language models on tokens. A robot's `types.Datum` holds what the robot saw and did at one frame instead:

```python
types.Datum(
    model_input=types.ModelInput(chunks=[
        types.ImageChunk(data=png_bytes, format="png", name="head"),
        types.StateChunk(name="left_arm", data=joint_positions),
        types.TextChunk(text="put the plastic bottles in the bin"),
    ]),
    loss_fn_inputs={"left_arm": action_chunk},
)
```

| Field | Holds |
|---|---|
| `ImageChunk(data, format, name)` | One camera image, encoded: `format` is `"png"` or `"jpeg"` and must match the bytes. `name` is the camera. |
| `StateChunk(name, data)` | One state array, such as an arm's joint positions. |
| `TextChunk(text)` | The task prompt. |
| `loss_fn_inputs` | The actions from this frame on, keyed by action name. |

Arrays can be NumPy arrays, torch tensors or `types.TensorData`; floats are sent as float32. `training_client.get_info().model_data` reports the names and sizes the model expects.

## GR00T N1.7

`nvidia/GR00T-N1.7` is NVIDIA's [GR00T N1.7](https://huggingface.co/nvidia/GR00T-N1.7-3B) vision-language-action model, trained with its flow-matching loss (`loss_fn="flow_matching"`).

`create_lora_training_client(base_model, rank=32, seed=None)` trains a LoRA of `rank`, at least 1, with alpha twice the rank. The adapters go on the linear layers of the diffusion action head, the vision-language self-attention and the robot's state and action projectors. The vision-language model stays frozen; the position embedding and the vision-language layer norm train in full. `seed` seeds the adapters. At rank 32, about 41M parameters train.

### Inputs

Every datum carries each camera, state and action the model was configured with, exactly once, and one prompt:

| Input | Shape | Type | Notes |
|---|---|---|---|
| `ImageChunk`, one per camera | `[H, W, 3]` when decoded | PNG or JPEG bytes | RGB, any resolution: GR00T resizes and crops each image itself. |
| `StateChunk`, one per state name | `[state_dims[name]]` | float32 | Raw values, such as radians. The server normalizes them. |
| `TextChunk` | | string | Exactly one per datum. |
| `loss_fn_inputs[name]`, one per action name | `[action_horizon, action_dims[name]]` | float32 | Absolute targets for this frame and the next `action_horizon - 1`. Where an episode ends sooner, repeat its last action. |

Send absolute actions, in the robot's own units. The server normalizes them and, for the actions its model predicts relative to the current state, such as arm joints, subtracts the state itself. A gripper stays absolute.

A datum whose names or shapes do not match fails with a `ValueError` that names the expected ones, before anything runs on the GPU.

### Outputs

| Call | Result |
|---|---|
| `forward_backward(data, "flow_matching")` | `ForwardBackwardOutput`: `metrics["loss:mean"]` is the batch's mean flow-matching loss, and `loss_fn_outputs` holds one `{"loss": TensorData}` of shape `[1]` per datum. |
| `optim_step(adam_params)` | `OptimStepResponse`: `metrics` holds `grad_norm` (before clipping), `learning_rate` and the model's `step`. |
| `save_weights_for_sampler(name)` | `SaveWeightsForSamplerResponse.path`: the full model with the LoRA merged in, about 12 GB, which a GR00T policy loads. |
| `save_state(name)` | `SaveWeightsResponse.path`: the trained weights (the LoRA adapters, position embedding, layer norm and projectors) and their AdamW state, about 470 MB, for `load_state(path)` (weights only) or `load_state_with_optimizer(path)`. [Hosted inference](#running-a-trained-policy) runs it by `name`. |
| `get_info()` | `GetInfoResponse.model_data`: `action_horizon` and the `image_names`, `state_dims` and `action_dims` above. |

A trained GR00T policy predicts `[action_horizon, action_dims[name]]` absolute actions for each action name from one frame of images, state and prompt, the same shapes as `loss_fn_inputs`.

`AdamParams` takes Tinker's defaults: `learning_rate=1e-4`, `beta1=0.9`, `beta2=0.95`, `eps=1e-12`, `weight_decay=0.0` and `grad_clip_norm=0.0`, where 0 turns clipping off. A rank-32 LoRA of GR00T trains well with `learning_rate=5e-4` and `grad_clip_norm=1.0`.

### Example: the ABC sim

The ABC sim's bimanual robot, two six-joint arms each with a gripper, uses:

| Input | Names | Shape |
|---|---|---|
| Cameras | `head`, `wrist_left`, `wrist_right` | `[224, 224, 3]` in its recordings |
| State | `left_arm`, `right_arm` | `[6]` joint positions, radians |
| | `left_gripper`, `right_gripper` | `[1]`, 0 closed to 1 open |
| Actions | the same four names | `[40, 6]` and `[40, 1]` |

```python
import numpy as np

ARMS = {"left_arm": slice(0, 6), "left_gripper": slice(6, 7), "right_arm": slice(7, 13), "right_gripper": slice(13, 14)}

def datum(images, state, actions, t, prompt, horizon=40):
    """images: {camera: PNG bytes}; state: [14] at frame t; actions: [T, 14] for the episode."""
    window = actions[t:t + horizon]
    window = np.concatenate([window, np.repeat(window[-1:], horizon - len(window), axis=0)])
    chunks = [types.ImageChunk(data=png, format="png", name=camera) for camera, png in images.items()]
    chunks += [types.StateChunk(name=name, data=state[part]) for name, part in ARMS.items()]
    chunks.append(types.TextChunk(text=prompt))
    return types.Datum(model_input=types.ModelInput(chunks=chunks), loss_fn_inputs={name: window[:, part] for name, part in ARMS.items()})
```

The server starts this robot's projectors from those of a pretrained GR00T embodiment with a similar layout, so its loss starts low. A rank-32 LoRA at batch 54 and `learning_rate=5e-4` takes about 3.7 s per `forward_backward` and `optim_step`, and its loss falls from about 0.12 at step 10 to about 0.04 by step 50.

## Running a trained policy

`robot.inference(prompt, lora=name)` runs GR00T N1.7 with the LoRA you saved with `save_state(name)` against a live robot. The policy runs on Adamo's GPUs: it watches the robot's cameras and publishes actions on its control channel, and nothing runs on your machine. Requires SDK 1.0.11 or later.

```python
import time
import adamo

training_client.save_state(name="abc-sim-r64-b256-500").result()

with adamo.Robot(name="abc-sim") as robot:
    with robot.inference("sim put the plastic bottles in the bin", lora="abc-sim-r64-b256-500") as run:
        while True:
            status = run.status()
            if status["policy_error"]:
                raise RuntimeError(status["policy_error"])
            if status["run"]:
                print("actions published:", status["run"]["actions_published"])
            else:
                print("policy", status["policy"], "- waiting to start")
            time.sleep(5)
```

Leaving the `with` block stops the run and releases the robot. `inference` returns as soon as the service accepts the request; `status()` and `stop()` work as for any [cloud inference](/v1/python-sdk/#cloud-inference) run.

- `lora` names a `save_state` checkpoint of this account's GR00T LoRA training. Use the name you saved it under, not the returned `path`. A `save_weights_for_sampler` save is a full model and cannot be run this way.
- `lora` on its own selects GR00T. `policy="gr00t"` without `lora` runs the base GR00T N1.7 weights, which have not been trained on your robot.
- Switching to another LoRA, even during a run, takes a fraction of a second. The first run of a prompt the policy has not seen compiles for about a minute first. After a cold start, the policy loads and compiles for up to about 10 minutes before the run starts.
- The policy predicts a 40-step chunk in about 23 ms, executes 20 steps of it at 30 Hz, and asks for the next chunk 8 steps before they run out.

The hosted GR00T policy is set up for [the ABC sim's layout](#example-the-abc-sim), and expects the robot to publish:

| Stream | Key | Format |
|---|---|---|
| Cameras | `{robot}/head`, `{robot}/wrist_left`, `{robot}/wrist_right` video tracks | `head` is a side-by-side stereo pair, and the policy uses its left half. Each image is letterboxed to 224×224, as in the recordings. |
| State | `{robot}/action/joints` | The joint target the robot applies: a big-endian u64 timestamp in µs, then 14 big-endian float32s, `[left_arm × 6, left_gripper, right_arm × 6, right_gripper]`. |
| Actions | `{robot}/control/joint_state` | Published by the policy as JointState JSON, 14 absolute joint targets in the same order. |

The ABC sim publishes all of these. `uv run --project sim/abc sim/abc/main.py --inference --lora abc-sim-r64-b256-500` in the [adamo repository](https://github.com/adamo-tech/adamo) starts the sim and the policy together.

Over HTTP, with your organization API key:

```bash
API=https://api.adamohq.com/api/inference
curl -X POST $API/start -H "X-API-Key: $ADAMO_API_KEY" -H 'content-type: application/json' \
  -d '{"robot_name": "abc-sim", "prompt": "sim put the plastic bottles in the bin", "policy": "gr00t", "lora": "abc-sim-r64-b256-500"}'
curl "$API/status?policy=gr00t" -H "X-API-Key: $ADAMO_API_KEY"
curl -X POST "$API/stop?policy=gr00t" -H "X-API-Key: $ADAMO_API_KEY"
```
