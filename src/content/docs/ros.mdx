<Aside type="danger" title="ROS adds latency and reduces stream reliability">
  Every ROS video frame crosses the DDS transport as raw pixels and is
  copied several times before it reaches the encoder, and compressed topics
  add a full decode/re-encode step. This adds latency on every frame and
  makes throughput depend on your ROS graph's health — a busy DDS domain,
  QoS mismatches, or a stalled publisher all degrade the stream in ways
  Adamo cannot correct. Use ROS inputs when the ROS graph is the only place
  the frames exist. For production teleop, attach cameras through
  [V4L2 or shared memory](/cameras/) instead — those paths feed the encoder
  directly.
</Aside>

Adamo connects to a robot's ROS 2 graph directly. Two things come out of that:

1. **Video** — a camera topic (`sensor_msgs/Image`, `CompressedImage`, or an H.264 stream) becomes a video track, hardware-encoded on the robot and streamed like any other camera.
2. **Control** — operator input (gamepad, VR) arrives as native ROS 2 topics that any local node can subscribe to, with no Adamo code in your control stack.

The bridge runs inside the robot process and speaks DDS to the local graph, so it works with stock ROS 2 (Humble, Jazzy, Kilted) using the default middleware. It needs no `rclpy`, no changes to your ROS installation, and no extra process. Nothing ROS-formatted leaves the robot: camera frames are encoded before they are published, and operator input arrives already in ROS wire format.

## Requirements

- ROS 2 nodes using a DDS middleware (the default on every current distro).
- A ROS-enabled Adamo build.
- `ROS_DOMAIN_ID` is honored; pass `domain_id` to override it.

```yaml
video_tracks:
  - name: "front"

    fps: 30
```

The topic name selects the input handling:

| Topic carries | Handling |
| --- | --- |
| Raw `sensor_msgs/Image` (`rgb8`, `bgra8`, `mono8`, `nv12`, …) | Encoded directly |
| `sensor_msgs/CompressedImage` (JPEG, topics ending in `/compressed`) | Decoded, then encoded |
| H.264 / `ffmpeg_image_transport` packets | Decoded, then re-encoded at your bitrate |

If the inference picks wrong, set the type explicitly in the config file: `ros_image`, `ros_compressed_image`, `ros_h264`, `ros_h264_transcode`, `ros_ffmpeg_packet`, or `ros_ffmpeg_packet_transcode`. The non-`_transcode` H.264 variants forward the stream as-is instead of re-encoding — cheap, but bitrate and keyframes stay whatever the ROS publisher produces, so adaptive bitrate does not apply.

Only topics attached to a track are read from the graph. The bridge creates a DDS reader when the track starts and destroys it when the track stops, so an idle Adamo integration costs your camera publishers nothing.

## Operator control as ROS topics

Enable the control fan-out and operator input from [operate.adamohq.com](https://operate.adamohq.com) is published into the local graph:

<TabItem label="Python" icon="seti:python">

The ROS 2 options (`attach_video(ros=...)`, `enable_ros_control`) are not available in the Python SDK 1.0. Use the config file with `adamo-network`.

</TabItem>
<TabItem label="Config file">

```yaml
ros:
  enabled: true
```

</TabItem>
<TabItem label="C" icon="seti:c">

```c
adamo_robot_t *robot = adamo_robot_new_default("ak_...", "my-arm");
adamo_robot_enable_ros_control(robot, 0);  /* domain_id 0 honors ROS_DOMAIN_ID */
adamo_robot_run(robot);
```

</TabItem>
</Tabs>

Your nodes then subscribe like to any other topic:

| ROS topic | Type | Source |
| --- | --- | --- |
| `/joy` | `sensor_msgs/msg/Joy` | Gamepad |
| `/head_pose` | `geometry_msgs/msg/PoseStamped` | VR headset pose |
| `/controller/{left,right}` | `geometry_msgs/msg/PoseStamped` | VR controller grip pose |
| `/controller/{left,right}/tip` | `geometry_msgs/msg/PoseStamped` | VR controller aim pose |
| `/controller/{left,right}/joy` | `sensor_msgs/msg/Joy` | VR controller axes and buttons |
| `/teleop/clutch` | `std_msgs/msg/Bool` | VR clutch state |

```python title="cmd_from_joy.py — plain rclpy, no Adamo imports"
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Joy

rclpy.init()
node = Node("teleop")
node.create_subscription(Joy, "/joy", lambda msg: print(msg.axes), 10)
rclpy.spin(node)
```

A message for a topic that no local node subscribes to is dropped on the robot — fan-out is driven by your graph's subscriptions. To additionally restrict which topics may be published at all, pass an allowlist:

```python
robot.enable_ros_control(control_topics=["/joy", "/teleop/clutch"])
```

<Aside>
  If you hand-decoded these payloads before (see [Receiving
  Control](/control/)), the fan-out replaces that code on ROS 2 robots: the
  same messages arrive as native topics instead of envelopes.
</Aside>

## Recording ROS topics

`record_ros` reads ROS topics from the local graph and publishes each message as JSON under the robot's name, where it is [recorded](/recording/#ros-topics) and can be subscribed to live. `/joint_states` on robot `my-arm` arrives on `my-arm/joint_states`. Declare each topic and its type when enabling ROS:

```python
ros = robot.enable_ros_control(subscribe_topics={
    "/joint_states": "sensor_msgs/msg/JointState",
    "/ee_pose": "geometry_msgs/msg/PoseStamped",
})
robot.record_ros(["/joint_states", "/ee_pose"])
```

Each message is stamped with the time the robot received it from ROS, on the same clock as the video. A message that waits on the robot behind a slow link still lines up with the frames from the moment it arrived. The original `header.stamp` stays in the message.

### Choosing reliable or best effort

`reliable` sets how messages leave the robot when the link cannot keep up. It applies to every topic in the call.

| | `reliable=True` (default) | `reliable=False` |
| --- | --- | --- |
| Delivers | Every message, in order | The newest message of each topic |
| When the link is slow | Queues up to 4096 messages or 32 MiB per topic and waits | Replaces the unsent message and never waits |
| `max_age` default | 1.0 s | 0.1 s |
| Use for | Data you train on or replay: joint states, commands, poses | Live readouts where only the current value matters |

`record_ros` is called once per robot, so pick the mode that suits all its topics:

```python
robot.record_ros(["/joint_states", "/ee_pose"])               # every message, in order
# or
robot.record_ros(["/battery_state"], reliable=False)          # newest only, never more than 100 ms old
```

A message that has waited longer than `max_age` to leave the robot is skipped. On a reliable recording, `max_age` is how long a network stall may last before messages are lost. Raise it for a link with long stalls. Lower it only if a late message is worse than a missing one.

<Aside type="caution" title="Best effort is for small messages">
  A large message is sent in fragments, and losing any fragment loses the
  whole message. Over a lossy link, best-effort messages of tens of kilobytes
  can almost all be lost. Keep large topics, such as many-joint states or point
  clouds, on `reliable=True`.
</Aside>

### Checking for loss

Messages that reach the bridge but do not leave the robot are counted in `ros_control_status()`:

```python
status = robot.ros_control_status()
status["recording_dropped"]  # not sent: beyond a full reliable queue, or replaced in best-effort mode
status["recording_stale"]    # skipped for waiting longer than max_age
```

A reliable recording that loses messages also prints a warning naming each topic, at most every 5 seconds:

```
adamo ROS recording fell behind: /joint_states dropped 120 (the queue holds 4096 messages / 32 MiB per topic). The link or this host is not keeping up with the topic rate: lower the publish rate or message size, or check the network. Totals are in ros_control_status().
```

In best-effort mode, replacements are the requested behaviour, so they are counted but not warned about.

When a ROS node starts publishing, its first message can be missed while DDS discovery connects it to the bridge. This is standard DDS behaviour for any newly matched subscriber.

### Reading topics in your own code

`RosSession.subscribe` returns only the newest message by default, which suits state. Pass `queue_size` to receive every message in order:

```python
with adamo.RosSession(subscribe_topics={"/joint_states": "sensor_msgs/msg/JointState"}) as ros:
    states = ros.subscribe("/joint_states", queue_size=1024)
    sample = states.recv(timeout=0.1)  # sample.cdr is the complete ROS message
    states.stats()["overwritten"]      # messages discarded because the queue was full
```

Video tracks always use the newest frame only. A late frame is never worth showing.

## Notes

- The bridge participates in local DDS discovery only. It does not extend your DDS domain off the robot, and remote operators cannot reach topics beyond the control fan-out.
- One robot process runs one bridge; all ROS video tracks and the control fan-out share it.
- Control topics follow the priority rules of the rest of the control plane — they are never queued behind video.
